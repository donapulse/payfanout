The `idempotency-key` sent to Adyen now also covers the merchant account and, on `/payments/details`, the submitted `details` and `paymentData`, because Adyen checks keys across the whole company account: two merchant accounts sharing a caller key no longer receive each other's stored responses, and each step of a multi-step 3-D Secure flow reaches Adyen while a repeated step is still deduplicated. A retry that spans the upgrade is not deduplicated against the request sent before it, so let in-flight captures, cancels and refunds settle before deploying; `deriveAdyenIdempotencyKey` now takes `{ merchantAccount, path, idempotencyKey, details?, paymentData? }`. Captures, cancels and refunds now reject, instead of resolving or throwing a `TypeError`, an acknowledgement without its own `pspReference` (a retryable `processing_error`), a capture or refund acknowledgement that echoes another amount or currency, which means the idempotency key was already used for an earlier request (`invalid_request`), and a 2xx response that is not a JSON object (a retryable `psp_unavailable`, also on `completePayment`). Errors Adyen sends with `transient-error: true` are retried at any status, `errorCode` 705 maps to `rate_limited`, HTTP 408 to a retryable `psp_unavailable`, and HTTP 501 and 5xx errors typed `validation`, `configuration` or `security` to a non-retryable `invalid_request` instead of a retried `psp_unavailable`. Refusal reason 31 (Issuer Suspected Fraud) maps to `fraud_suspected`, and `refundPayment` sends the refund `reason` as Adyen's `merchantRefundReason`.
