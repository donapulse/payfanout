Classify PayZen's `PSP_` codes as the server adapter does, through the same map, whether `KR.onError` reports them or they sit on an unpaid order's last transaction. A failed, abandoned or timed-out 3-D Secure challenge (`PSP_539`) is now a non-retryable `authentication_required` instead of a retryable `processing_error` or a decline; an issuer's refusal of the authentication (`PSP_707`) and the refusals PayZen documents (`PSP_003`, `PSP_625` and the like) are `card_declined`, a risk-module decline is `fraud_suspected`, an authentication the issuer could not run (`PSP_708`) is `processing_error`, and `PSP_052` to `PSP_055` read as `AUTH_100` to `AUTH_103` do. A `PSP_` code the map does not list now reads as `processing_error` on an unpaid transaction too, where it read as `card_declined`, and `PSP_` answers from `KR.onError` are no longer retryable unless they report an outage or a rate limit, so a smartForm host that retries on a retryable failure stops retrying on them. A `PSP_` code's own `detailedErrorCode` is no longer read as an acquirer's refusal code.
